Investigation and validation were completed locally before release authorization.

the results below record pre-release validation, not App Store approval or distribution.

## NAS / offline continuation

Added a final byte-count check before a completed SMB partial replaces an offline-ready file.
A generated Mango transfer reproduced the shared transport returning at early EOF without an
error. Earmark had the same unchecked promotion path. Both now reject a short file and retain
partial bytes for retry, using fresh filesystem attributes rather than cached URL resource values.
Transfer state and background registration are injectable for isolated integration tests; their
production defaults are unchanged.

## Background transfer lifecycle

Confirmed failures included automatically restarting explicitly cancelled jobs in a background
execution, losing Cancel when restoring an in-flight job, and allowing an old background budget
to remain active after foreground activation. Both apps now preserve system-interrupted work
separately from explicit user cancellation, complete each execution once, reject stale expiry
callbacks, and hand control to foreground before an old expiry can pause transfers.

Earmark also lost Cancel's persisted intent in eight of eight immediate disk checks because its
queue write was asynchronous. Cancel and Retry now flush their control intent before returning;
progress writes retain the existing asynchronous generation ordering. Old queue JSON still decodes.

The injectable `TransferBackgroundExecution` adapter exercises the real manager's callback and
completion boundary without constructing a system-owned BGProcessingTask. It does not prove
when iOS grants background processing time.

## Replaced sources during partial-download retry — 2026-10-21

Cancelling a real SMB transfer, replacing its generated WAV with different equal-sized valid
audio, and retrying falsely marked mixed audio complete. Both apps now associate partials
with source endpoint/path, fresh size, modification time and bounded first/last SHA-256
samples. Unknown, legacy, corrupt, changed and oversized partials restart. Queue totals use
the current source size. Completed length and source snapshot are checked before promotion,
and successful promotion removes the hidden partial sidecar.

Metadata and samples alone proved insufficient: changing 64 KiB inside the retained prefix
while preserving size, timestamp and sampled ends still produced outdated audio. Retry now
compares all retained bytes with live SMB reads before appending. The comparison uses bounded
chunks, preserves verified local bytes and honors cancellation. It rereads that prefix over
the network because the API supplies no immutable version identifier.

- `/tmp/earmark-replaced-source-red-20261020.xcresult`: equal-sized replacement mixed versions.
- `/tmp/earmark-replaced-source-green-20261021.xcresult`: same-size, growing, preserved-date
  replacement and unchanged cancel/retry/offline/removal passed with the initial snapshot fix.
- `/tmp/earmark-middle-source-change-red2-20261021.xcresult`: a middle-only edit failed that fix.
- `/tmp/earmark-source-prefix-green-20261021.xcresult`: middle-only replacement, rejection of
  a detected change during download, and unchanged cancel/retry/offline/removal all pass with
  full retained-prefix comparison.
- `/tmp/earmark-partial-integrity-all-20261021.xcresult`: all 14 real-SMB cases pass with the
  final prefix verification, including replacement variants, unchanged retry, service loss,
  streaming recovery, switching to local audio and all three background/foreground cases.
- `/tmp/earmark-integrity-full-20261021.xcresult`: all 249 ordinary unit/integration tests
  pass on iPhone 17 Pro, iOS 26.5, after final retained-prefix verification, including the
  nine partial-source policy cases and previous playback/widget/background regressions.
  Scoped SwiftLint has one existing warning and no errors; `git diff --check` passes.
  After both apps' network suites finished, the owned fixture controller and child stopped;
  no port-1445 listener or control-session file remained.

The pre/post snapshots do not make concurrently edited NAS files transactional: an active
writer preserving metadata and changing unsampled bytes during the transfer can still evade
snapshot detection. The pre-existing completed-destination shortcut is outside this fix.

## Verification

### Actual SMB service loss and stalled playback

The loopback fixture controller now terminates its owned SMB child process, closing live
connections, and starts a new process. Tests use the same app client across that restart.
This reproduced a playback failure that a manual client disconnect had not exposed: seeking
beyond buffered audio while the service was absent left Earmark showing playback as active
for over 20 seconds, with no error or Retry path. The loader had logged read errors, but
AVPlayerItem remained ready rather than failed; its time-control state moved to waiting.

`SMBResourceLoader` now reports read failures to the active player. Delivery checks item
identity/generation and cancellation, and replaced items remove the observer. The player uses
its existing network-error/Play-to-retry path. The loader also records failure before queuing
main-actor delivery: an immediate Play can then reload the failed item even if its error callback
has not arrived. Without that producer-side state, an old range error could arrive after a
seek/Play and stop the newly requested position. A local book selected while old remote reads
fail remains playing.

## Remote WAV playback on iOS 27

The final device-wording check exposed a separate playback defect: both existing streaming
recovery cases failed before the planned outage on iPad Pro, iPadOS 27.0. AVPlayer rejected
the initial generated WAV with AVFoundation -11800 / underlying OSStatus -17770. The same
case passed on iPhone iOS 26.5 and failed on iPhone iOS 27.0, isolating the runtime boundary
from the iPad layout. The source file and delivered RIFF/WAVE header were valid.

Ranked probes distinguished runtime behavior, incorrect delivery/type information, and
fixture timing. Serializing delivery on the loader queue did not help; that probe was
reverted. Removing the service's artificial read delay did not help either. A generated
AAC/M4A probe started successfully; its outage case then failed because the small file had
already been buffered, so that result is not represented as a recovery pass.

Enabling precise timing restored WAV startup. The final change requests it only for WAV,
using the scanner's container hint when present and the path extension otherwise. Other
formats keep the caller's existing timing preference. With the normal 0.03-second read
delay restored, both original cases passed on Pro: a lost service offers Retry at 150s,
and a failed old remote read does not interrupt the newly selected local book. The trace
shows startup after the first 1 MB and a 44 KB tail range of a 17 MB file, rather than a
whole-file download. The trace was then removed from production code.

Evidence retained in `/tmp`:

- `earmark-device-message-streaming-20261021.xcresult`: both Pro cases failed at initial
